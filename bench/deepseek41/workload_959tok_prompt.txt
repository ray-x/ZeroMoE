You are the senior reliability engineer responsible for a multi-region object storage service used by hospitals, research labs, and financial firms. The service accepts immutable objects, supports versioned updates through manifests, and returns objects through signed URLs. Each region has three storage zones, a metadata database, an asynchronous replication queue, and a fleet of stateless API servers. Customers expect strong durability, predictable read latency, and a clear audit trail. The service has recently grown from a few petabytes to tens of petabytes, while the operations team and on-call staffing have not grown at the same rate. Prepare a practical design review for the next year of operation.

Use these operating constraints. A region may lose one storage zone without losing acknowledged data. A region-wide network partition can last several hours. Writes should remain available in at least one healthy region, but the service must not falsely report a write as globally replicated. Object data may contain regulated information, and data deletion requests must eventually remove all physical replicas and derived cache entries. The API has a p99 read latency target of 200 ms for local reads and a p99 write acknowledgement target of 500 ms. Replication traffic shares links with customer reads during normal operation. The metadata database is replicated separately from object data, which creates a risk that one side advances while the other side is delayed.

A recent incident began when a maintenance change reduced the free space target on one storage zone. Compaction fell behind, and the allocator continued accepting writes until that zone had only a small amount of usable space. The API then retried writes against another zone, increasing network traffic and queue depth. At the same time, replication lag rose in a second region. Some API servers returned success after durable local acknowledgement, while the customer status page implied that every write had already reached both regions. A later repair job replayed old manifest updates and temporarily made several object versions appear in the wrong order. No acknowledged object was permanently lost, but the incident took hours to understand and customers could not tell which copies were current.

Analyze the incident as a system-design problem, not only an operational mistake. Separate the safety properties that must always hold from latency and availability goals that may be degraded during a partition. Explain how write acknowledgement should describe local durability, zone replication, and cross-region replication. Identify which metadata and object-data state must move together, how to prevent a manifest from referencing an object version that has not been durably stored, and how repair jobs can avoid resurrecting stale state.

Propose a capacity policy for each storage zone. Include the space needed for compaction, repair, rebalance, metadata growth, and temporary write amplification. Describe admission control and retry behavior when one zone approaches its safe limit. Explain how to keep retries from multiplying load during congestion and how to prioritize customer reads, replication, repair, and deletion work when network or disk capacity is scarce. Include a backpressure strategy that protects the healthy zones instead of allowing one degraded zone to destabilize the entire region.

Design the replication state machine for a write. Define the states visible to the API and to customers, including locally durable, zone-replicated, region-replicated, delayed, and repair-required. State which transitions are monotonic and which may be rolled back. Explain how the service records replication acknowledgements across a network partition and how a reconnecting region reconciles concurrent manifest updates without silently discarding a committed version. Address idempotency keys, duplicate delivery, out-of-order messages, and partial retries.

Provide an operational plan with concrete signals and actions. Include metrics for per-zone usable bytes, compaction debt, write amplification, replication lag by age and bytes, retry rate, queue depth, repair throughput, deletion backlog, and the fraction of reads served from each region. Give alert thresholds that provide warning before the service reaches a hard capacity boundary. Define a staged response for a single-zone failure, a region partition, and a prolonged replication backlog. Explain how an on-call engineer can determine whether a write is merely local, fully replicated, or awaiting repair.

Finally, describe a small set of failure-injection exercises for a pre-production environment. Cover abrupt zone loss during writes, delayed metadata replication, duplicate and reordered replication events, compaction starvation, disk-full behavior, and a deletion request while replicas are offline. For each exercise, state the invariant to verify, the observable evidence to collect, and the condition that should stop the exercise. End with a prioritized implementation plan for the next two quarters, calling out the three highest-risk gaps and the measurable acceptance criteria for each.
