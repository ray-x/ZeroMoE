Design 4.1 What a family provides cpp struct FamilyDescriptor { ModelSpec spec; // dims, per layer types, router spec, quant types in use AttentionFactory attention; // layer > AttentionBlock LayerPlan plan; // per layer: attention + FFN block + residual style ProfileOverrides overrides; // optional, sparse, each with a reason (4.2) }; Interfaces (graph build time only; no per token cost): AttentionBlock : state_spec(layer) (KV heads/widths/window, recurrent state), declare_inputs() / set_inputs() for its own host inputs (positions, masks, KV row tables), and build(x, layer, phase, S) . The skeleton allocates state from state_spec . FfnBlock : a dense SwiGLU block, or the shared MoE block. A model may mix them per layer (MiMo layer 0 is dense, layers 1–47 are MoE). LayerPlan owns the residual structure. DeepSeek V4.1 hyper connections keep several residual streams; an interface covering only attention and FFN would not fit it. Everything else is the skeleton's: layer loop, MoE block, placement, offload tier, early ready lane, prefill chunking and continuation, op offload policy, VRAM/coverage preflight, standard report. 4.2 Settings: one resolved value per knob, with a source common defaults → family overrides → profile (frozen, measured) → run config (TOML / env) Common defaults : one struct with every tunable (lane threads, prefill chunk and minimum batch, op offload policy and threshold, arena pinning, assist slots, cache headroom policy, …). Family overrides : optional fields. Each override carries a mandatory reason (e.g. GLM: "512 token chunks measured 90 vs 250 tok/s"). An override equal to the default is rejected as redundant. Profile : the R4 ExecutionProfile — validated, measured values for a key (hardware × model dims × quant signature × budgets × workload). Run config : TOML/env, for tuning one model or run without a code change. At startup the resolver prints every knob with its value and source, e.g. prefill_offload off family:ling (reason: …) / moe_cache_gb[0] 12 toml . Tension with R4, and the proposed resolution. R4 §5 makes profiles immutable once frozen so a re tune never silently changes another run. Requirement 3 needs a change to a common default to propagate. These agree only if a profile pins just the fields it measured and every other field keeps following the defaults. A pinned field is frozen with its provenance (changed only by an explicit re baseline); an unpinned field follows the live default. So: profiles store a sparse set of pinned values, not a full copy of the settings. Decided: adopted. Drift guard. Following live defaults means a large change to a common default (say prefill_chunk ) can change a frozen profile's behaviour without anyone re baselining it. So each profile records, when frozen, a baseline_default_hash (computed from the table of common defaults, so parallel branches do not conflict on a version number) and the baseline values of the unpinned fields it was measured with. At startup the resolver compares them with the live ones. A mismatch is a preflight warning (an error in performance mode): "profile measured with chunk=128, live default is 512 — re tune or pin it." The change is therefore visible, not silent, and fixing it is an explicit re baseline. The drift check is part of R4's decision, not an addition on top of it. The hash covers only fields that can change performance or numerics. Benign fields (log level, file paths, report formatting) are masked out, listed in one place, so changing them never trips the guard. Enforcement matches the preflight policy: warning in development, hard failure in performance mode . Only a failure honours R4's rule against silent execution changes; the user must accept the new baseline or re tune. Fallback if R4 rejects sparse profiles: full snapshotting. A profile freezes every resolved default at creation; the engine rejects a mismatch until an explicit rebase profile run updates the frozen file and flags it for re measurement. This keeps R4 intact but gives up automatic propagation (requirement 3): every common default change then needs a rebase pass over all profiles. Capabilities are a separate resolved table.
